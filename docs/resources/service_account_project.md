# mixpanel_service_account_project (Resource)

Associates a service account with a project — grants the service account access to the project so it can perform API operations within that project's scope.

This resource owns one project membership separately from the service account.
Changing its key or payload removes and recreates the membership; it does not
recreate the account or rotate its credentials. Keep the account resource stable
and omit inline `mixpanel_service_account.projects` configuration when standalone
association resources own those memberships. Managing the same grant in both
places gives Terraform competing owners and inline project changes can replace
the service account.

## Example Usage

```terraform
resource "mixpanel_service_account_project" "terraform_prod" {
  organization_id = 7654321
  key             = "987654:1234567"
  payload         = jsonencode({
    serviceaccount_id = 987654
    project_id        = 1234567
  })
}
```

Refresh selects the numeric service account `id` and then the numeric project
`id` within its `projects` list. It removes state when that pair is absent.
Malformed lists and API errors produce diagnostics rather than deleting state.

Refresh uses the typed service-account collection route
`/api/app/organizations/{organization_id}/service-accounts`. Create/delete retain
the existing legacy `/organizations/{organization_id}/add-to-project/` and
`remove-from-project/` routes; these write routes have not been live-validated.

The documented add/remove request fields are `serviceaccount_id` and `project_id`.
The API exposes project roles in its read response, but acceptance of a `role`
field by the add endpoint has not been verified. This provider passes the payload
through unchanged on create/delete and does not establish a new role-write API
contract. If a caller explicitly includes `role` in its payload, refresh copies
the observed role into that field so drift can produce a replacement plan. It
does not add a role field to payloads that omit it. Verify the endpoint's role
contract before relying on role changes through this resource.

The tests exercise nested mock HTTP responses and Terraform state/lifecycle
behavior. They are not live API validation of permissions or accepted role fields.

## Schema

### Required

- `key` (String) Read-selection key for this association (composite key identifying the service account and project association (format: serviceaccount_id:project_id)). Changing it forces a new association.
- `payload` (String) jsonencode'd request body for the create/delete verbs (the API bodies are untyped). Changing it forces a new association.

### Optional

- `organization_id` (String) Organization ID. Defaults to the provider organization.

### Read-Only

- `id` (String) Synthetic composite identity: "<organization_id>:<key>".

## Import

Import using the composite identifier `ORGANIZATION_ID:SERVICE_ACCOUNT_ID:PROJECT_ID`:

```terraform
import {
  to = mixpanel_service_account_project.terraform_prod
  id = "7654321:987654:1234567"
}
```

Import sets `organization_id`, `key`, and a minimal numeric payload containing
`serviceaccount_id` and `project_id`. It does not infer a writable role from the
read response. Match the imported resource configuration to that payload; adding
or changing payload fields plans membership replacement.
